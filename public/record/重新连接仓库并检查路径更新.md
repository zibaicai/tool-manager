# ToolManager 能否在 Kali 上运行？

**结论：不能直接用。** 这是一个以 Windows 为目标平台的 Tauri 应用，核心交互（命令行窗口、UAC 提权、EXE/PE 检测、自定义窗口边框）都是 Windows 专属；在 Kali（Linux）上能编译出壳，但关键功能会报错或失效。

## 各模块在 Kali 上的状态

| 模块 | Kali 上状态 | 原因 |
|---|---|---|
| Vue 前端界面、设置、分类、scanRoot | ✅ 可用 | 纯前端，跨平台 |
| 背景图/asset 协议、read_text_file 目录限定、配置持久化 | ✅ 可用 | Tauri 核心，跨平台 |
| EXE 工具启动（非 Windows 分支） | ⚠️ 半可用 | [launcher.rs L246](file:///d:/ScriptingTool/ToolManager/src-tauri/src/commands/launcher.rs#L246) 走 `sh -c "$path $args"`，对 Linux ELF/脚本可用，但 `.exe` 需 Wine |
| **CMD 工具启动** | ❌ 不可用 | [launcher.rs L238](file:///d:/ScriptingTool/ToolManager/src-tauri/src/commands/launcher.rs#L238) 非 Windows 分支直接 `Err("当前仅支持 Windows 命令行窗口")` |
| **管理员提权** | ❌ 不可用 | 仅 `#[cfg(windows)]` 的 `ShellExecuteExW` + `runas`（UAC），Linux 分支忽略 admin 参数 |
| 控制台/GUI 区分 | ❌ 不可用 | `is_console_exe` 读 PE 头，Linux 无意义 |
| 自定义窗口边框（无边框+拖拽） | ⚠️ 残缺 | `winframe` 模块是 `#[cfg(windows)]`（DWM + 命中测试），Linux 下窗口无边框且无法拖拽标题栏 |
| 工具扩展名白名单 | ❌ 不匹配 | `PROGRAM_EXTENSIONS = ["exe","bat","cmd"]`，Kali 工具多为无后缀 ELF / `.sh` / `.py` |
| deploy.ps1 部署 | ❌ 不可用 | Windows 专用（winget / MSVC / `.lnk`） |

## 若要在 Kali 上用，需要做的移植

1. **CMD 工具启动**：实现 Linux 版 `open_cmd_window`，调用系统终端（`x-terminal-emulator` / `gnome-terminal` / `xfce4-terminal`）`--working-directory <path>`。
2. **提权**：`admin=true` 时用 `pkexec` 或在终端内 `sudo`。
3. **可执行文件判定**：Linux 下用 `std::fs::metadata` 的 `mode & 0o111` 判定可执行位，而非扩展名；扩展名白名单改为可选过滤。
4. **窗口边框**：Linux 下启用原生装饰（`decorations: true`，Tauri 支持按平台配置），或用 `appWindow.startDragging()` 做标题栏拖拽。
5. **构建依赖**：Kali 上需装 `webkit2gtk-4.1`、`libayatana-appindicator3-dev`、`build-essential`、`libssl-dev`、`curl`、`wget`、`file`、`libxdo-dev`、`libgtk-3-dev`、`libwebkit2gtk-4.1-dev`、`libsoup-3.0-dev`、`libjavascriptcoregtk-4.1-dev`，然后 `cargo tauri build`。

## 概念适配度

ToolManager 的模型（分类 + 文档 + 图标 + 一键启动）其实挺适合 Kali —— Kali 本身就是按类别组织的上百个工具。但它的**工具发现机制是"扫描一个根目录下的子目录=一个工具"**，更适合你自己整理的 `~/tools` 目录，而不是 Kali 扁平的 `/usr/bin`。如果要在 Kali 上深度用，工具录入方式也得调整。
