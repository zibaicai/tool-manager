### 为什么当初要分这两类

回看你的设计演化：

- **CMD 类**：`scanPath` 扫目录 → 每个子目录是一个工具 → 启动行为是"在该目录开终端"
- **EXE 类**：手动录入路径 → 启动行为是"直接 spawn 或提权"

这是**"发现方式 + 启动方式"的双重差异**，不是"文件类型"的差异。合并后，你会立刻遇到：

1. **扫描逻辑没法统一**：CMD 是"扫一级子目录"，EXE 是"用户输入单文件路径"。一个目录扫描项，和一个文件路径项，放进同一个列表，数据结构就开始别扭。
2. **"打开目录"按钮语义不同**：CMD 工具的"目录"就是工具根目录；EXE 工具的"目录"是 exe 的父目录。用户预期不一样。
3. **文档来源不同**：CMD 的 README/Ops 是约定在工具目录下自动探测；EXE 的文档路径是用户手动指定的（可能跟 exe 根本不在同一目录）。
4. **UI 排序混乱**：你之前按 title 排序，但 CMD 是"扫出来的批量"，EXE 是"手动加的零散"，合并后列表会混在一起，用户很难定位。

### 但你现在的真实痛点可能是

**用户视角看，分类不该是"cmd/exe"，而该是"Web 扫描 / 主机扫描 / 信息收集"这种业务分类。**

从你之前发的那张截图看，左侧已经有"Web 扫描"、"主机扫描"、"接口扫描"、"框架扫描"这些业务分类，还有"Web扫描(EXE)"、"主机扫描(EXE)"这种带后缀的重复分类——**这才是真正的问题**。

你现在不是要合并 cmd/exe 两个大类，而是要**把 "cmd/exe" 从"一级分类"降级为"工具属性"**。

### 正确的架构调整

**一级分类**：业务维度（Web 扫描、主机扫描、信息收集……）
**工具属性**：启动方式（cmd/exe）、语言、是否需要提权

```
├─ 主机扫描
```

一个分类下，**同时容纳扫描型和手动型条目**。工具卡片上的 `CMD`/`EXE` 标签保留，作为**视觉提示**，不再是分类维度。

### 这样做的好处

1. **用户按"我想干什么"找工具**，而不是按"这个工具是什么格式"找工具
2. **`cmd`/`exe` 标签仍然保留**，作为卡片上的标识，启动分流逻辑不变
3. **分类可以从 menu.json 自由配置**，你想加"应急响应"、"内网渗透"随时加
4. **扫描/手动的差异下沉到"条目类型"**，不影响上层 UI

### 什么情况下才真的合并分类

**只有一种情况**：你确认自己**永远不会按业务维度组织工具**，所有工具就是"能跑就行"，那么把 cmd/exe 合并成一个"全部工具"分类也不是不行。但看你的截图，你显然已经在按业务分类了。

### 具体建议

**不做**：合并 cmd 和 exe 两个大类
**做**：把 cmd/exe 从分类层下沉到条目属性层，一级分类改为纯业务维度

工作量评估：

- 数据结构：`Category` 里加 `entries` 支持混合类型（~1 天）
- 扫描逻辑：`scan_cmd_tools` 后合并到目标分类（~0.5 天）
- UI：卡片加 `type` 标签、分类渲染去掉"(EXE)"后缀（~1 天）
- menu.json 迁移：手工重排一次（~1 小时）

**总共 2~3 天**，换来的是长期更符合直觉的信息架构。

### 一句话回答

**cmd 和 exe 不该合并成一个大类，但也不该继续当"一级分类"。** 它们应该降级为工具的属性标签，一级分类让位给业务维度（Web 扫描 / 主机扫描 / 信息收集……），一个业务分类下可以同时放扫描型工具和手动录入型工具。

```
  id: string;
  title: string;

  docPath: string | null;
  icon: string | null;
  categoryId: string;

  source: ToolSource;      // 从哪来
  launchMode: LaunchMode;  // 怎么跑（保留 CMD/EXE 标签）

  available: boolean;
  favorite?: boolean;
  lastUsed?: number;
}

export interface Category {
  id: string;
  name: string;
  icon?: string;

  /** 扫描型来源：目录路径。存在则自动扫描该目录的一级子目录 */
  scanPath?: string;

  /** 手动型来源：直接内联工具条目 */
  entries?: ManualEntry[];
}

export interface ManualEntry {
  id: string;
  title: string;
  path: string;
  docPath?: string;
  launchMode: LaunchMode;  // 手动录入时由用户选择 cmd 或 exe
}

  categories: Category[];
}
```

## 五、扫描 + 组装逻辑（Store 层）

### 5.1 前端 Store 组装

ts

```
// src/stores/tools.ts
import { defineStore } from 'pinia';
import { ref, computed } from 'vue';
import type { Category, Tool } from '../types';
import { loadMenuConfig } from '../api/config';
import { scanCmdTools } from '../api/fs';

export const useToolsStore = defineStore('tools', () => {
  const categories = ref<Category[]>([]);
  const tools = ref<Tool[]>([]);
  const activeCategoryId = ref('');
  const loading = ref(false);
  const error = ref<string | null>(null);

  const activeTools = computed(() =>
    tools.value.filter((t) => t.categoryId === activeCategoryId.value)
  );

  async function init() {
    loading.value = true;
    error.value = null;
    try {
      const menu = await loadMenuConfig();
      categories.value = menu.categories;
      if (categories.value.length > 0) {
        activeCategoryId.value = categories.value[0].id;
      }
      await reloadAll();
    } catch (e: any) {
      error.value = String(e);
    } finally {
      loading.value = false;
    }
  }

  async function reloadAll() {
    const all: Tool[] = [];

    for (const cat of categories.value) {
      // 1. 扫描型：目录下的一级子目录
      if (cat.scanPath) {
        try {
          const scanned = await scanCmdTools(cat.scanPath, cat.id);
          // 扫描出来的都是 cmd 模式（或按需在 Rust 侧判定 launchMode）
          all.push(...scanned.map(t => ({ ...t, source: 'scan', launchMode: 'cmd' })));
        } catch (e) {
          console.warn(`扫描分类 ${cat.name} 失败:`, e);
        }
      }

      // 2. 手动型：内联 entries
      for (const entry of cat.entries || []) {
        all.push({
          id: entry.id,
          title: entry.title,
          path: entry.path,
          docPath: entry.docPath ?? null,
          icon: null,
          categoryId: cat.id,
          source: 'manual',
          launchMode: entry.launchMode,
          available: true,   // 后续可以加后台异步校验
        });
      }
    }

    tools.value = all;
  }

  function setActiveCategory(id: string) {
    activeCategoryId.value = id;
  }

  return { categories, tools, activeCategoryId, activeTools, loading, error, init, reloadAll, setActiveCategory };
});
```

## 七、迁移工具（一次性运行）

写一个独立命令，把旧 `menu.json` 转成新结构，避免用户手工重排。

```
// src-tauri/src/commands/migrate.rs
use crate::models::*;

#[tauri::command]
pub fn migrate_menu_config_if_needed() -> Result<bool, String> {
    let path = config_path("menu.json");
    let raw = std::fs::read_to_string(&path).map_err(|e| e.to_string())?;
    let old: OldMenuConfig = serde_json::from_str(&raw).map_err(|e| e.to_string())?;

    if old.version.unwrap_or(1) >= 2 {
        return Ok(false); // 已是新版
    }

    // 按 name 前缀把 "(EXE)" 类和对应 scan 类合并
    let mut new_cats: Vec<Category> = vec![];
    let mut name_to_scan: std::collections::HashMap<String, Category> = Default::default();

    // 第一遍：处理 scan 类
    for c in &old.categories {
        if c.category_type.as_deref() == Some("scan") {
            let name = c.name.trim().to_string();
            let cat = Category {
                id: c.id.clone(),
                name: name.clone(),
                icon: None,
                scan_path: c.scan_path.clone(),
                entries: vec![],
            };
            name_to_scan.insert(name, cat);
        }
    }

    // 第二遍：处理 manual 类，尝试并入同名 scan 类
    for c in &old.categories {
        if c.category_type.as_deref() == Some("manual") {
            // "Web扫描(EXE)" → 找 "Web扫描"
            let base = c.name.replace("(EXE)", "").trim().to_string();
            if let Some(target) = name_to_scan.get_mut(&base) {
                // 合并到已有分类：把旧 exe-tools.json 里的条目搬进来
                // 这里假设你之前用 exe-tools.json 单独存
                // ...（读 exe-tools.json 按 categoryId 匹配）
            } else {
                // 找不到对应 scan 类，作为纯手动分类保留
                new_cats.push(Category {
                    id: c.id.clone(),
                    name: c.name.clone(),
                    icon: None,
                    scan_path: None,
                    entries: vec![],
                });
            }
        }
    }

    // 组装最终配置
    let mut final_cats: Vec<Category> = name_to_scan.into_values().collect();
    final_cats.extend(new_cats);

    let new_cfg = MenuConfig { version: 2, categories: final_cats };
    std::fs::write(&path, serde_json::to_string_pretty(&new_cfg).unwrap())
        .map_err(|e| e.to_string())?;

    Ok(true)
}
```

**建议**：**不写兼容层**，直接用迁移工具一次性切过去。你的用户是自己，成本最低。

## 十、一句话总结

**把 `cmd/exe` 从分类维度降级为工具属性标签**，一级分类交给业务维度。一个业务分类下可以同时容纳"扫描型工具"和"手动录入工具"，UI 上通过卡片标签（蓝色 CMD / 橙色 EXE）区分启动方式，启动分流逻辑完全不变。

**核心改动**：

- `Category` 新增 `entries` 字段，`type` 字段删除
- `Tool` 的 `type` 拆成 `source` + `launchMode`
- `menu.json` 升到 `version: 2`，用迁移工具一次性转换
- 侧栏去掉 "(EXE)" 后缀，卡片保留 CMD/EXE 视觉标签

# 二、对上述参考意见的回馈

我仔细读了文档，也确认了当前代码结构。先上结论： 方向是对的，但建议的改动范围偏大、工作量评估偏乐观，且当前架构其实已经部分支持"混合"——痛点更多在 UI 展示层而非数据结构层。

下面逐条拆解可行性。

## 一、当前架构的真实状态
层面 现状 数据结构 `Category` 有`type: 'scan' | 'manual'` ，`Tool` 有`tool_type: 'cmd' | 'exe'` 存储 `menu.json` 存分类，`cmd-tools.json` 存扫描覆盖，`exe-tools.json` 独立存手动录入 后端扫描 `scan_all_cmd_tools` 只扫`category_type == 'scan'` 的分类 后端分配 `assign_cmd_tool` 检查目标分类必须是`scan` 类型且工具在扫描根下 前端录入 `ExeToolEditDialog.vue` 中 已经允许把 EXE 录入到 scan 分类 （过滤出所有 scan 分类供选择） 前端展示 `categories` store 通过`computed` 合并`cmdStore.tools + exeStore.tools` ，按`categoryId` 过滤展示

关键发现 ：EXE 工具 已经可以被分配到 scan 分类 了。当前左侧栏出现 "Web扫描" 和 "Web扫描(EXE)" 并列，不是因为数据结构限制，而是因为：

1. 你手动建了两个分类（一个 scan、一个 manual）
2. 侧边栏直接按`categories` 遍历，没有按 name 合并
## 二、文档建议的改动范围 vs 实际影响
文档给出的 2-3 天工作量，我评估下来 保守需要 5-7 天 ，核心遗漏了以下复杂度：

### 1. 后端存储层不是简单"append"
当前`exe-tools.json` 的`ExeToolEntry` 结构：

```Rust
struct ExeToolEntry {
    id, exe_path, category_id,
    args, title, desc, admin,
    stop_path, stop_admin,
}
```

如果把它塞进`Category.entries` ，`MenuConfig` 就变成 全量写回 （每增删一个 EXE 都要重写整个`menu.json` ）。而当前`exe-tools.json` 只改一条记录。对于频繁增删工具的场景，全量写回有损坏风险。

### 2. cmd-tools.json（override）的隐式依赖
扫描型工具的覆盖项（标题、手动分配、副标题）存在`cmd-tools.json` ，以工具`id` 为键。如果分类结构变了（比如 manual 分类被合并到 scan 分类，categoryId 变了），这些覆盖项的`category_id` 会指向不存在的分类，需要迁移逻辑处理。

### 3. read_text_file 安全边界
文档读取的范围校验依赖`exe_tool_dirs()` ，它从`exe-tools.json` 收集路径。如果 EXE 工具改存在`menu.json` 的`entries` 中，这个函数需要重写。

### 4. TS 类型连锁反应
`Tool` 结构一变 →`ts-rs` 重新生成`bindings.ts` → 所有`tool.type === TOOL_TYPES.EXE` 的 20+ 处判断都要改（ToolCard、ContentArea、ExeToolEditDialog、ConfirmDeleteDialog...），还有`Category` 的`type` 字段被删后，所有依赖`CategoryType` 的地方都要重构。

### 5. Kali 端同步成本
项目记忆中明确记录"双平台真机验证"是标准流程。Windows 改完结构，Kali 端必须同步，否则两边数据格式不一致。

## 三、三个可行方案对比
方案 改动范围 工作量 效果 风险 A. UI 层最小改动 不改数据结构，只改侧边栏展示逻辑：按 name 去重合并 scan + manual 分类，工具卡片加 CMD/EXE 标签 0.5-1 天 视觉上消除 "(EXE)" 后缀并列 代码有点 hacky，但无数据风险 B. 删`Category.type` + 保留双存储 删除`type` 字段，Category 增加可选`entries` ，但 EXE 仍存`exe-tools.json` 2-3 天 数据结构到位，存储层不变，为将来完全合并做准备 中等，需要写迁移 C. 文档建议的完整方案 合并存储、改`Tool` 结构、`source` +`launchMode` 、重写所有 Store 5-7 天 最彻底，长期最干净 高，涉及全链路重构

## 四、我的具体判断
方案 A 当前最实际 ：你的痛点（"(EXE)" 后缀并列）完全可以通过前端展示层解决，不需要动数据结构。

具体做法：

1. `categories` store 的`sortedCategories` 改为按 name 分组，同 name 的 scan + manual 合并为一个虚拟分类
2. `activeTools` 同时展示该 name 下所有 scan 工具和 entries
3. 工具卡片保留`tool_type` 标签（蓝色 CMD / 橙色 EXE）
这样：

- 侧边栏显示 "Web扫描 (7)" 而不是 "Web扫描" + "Web扫描(EXE)"
- 同一分类下同时展示 JSFinder(CMD) 和 BurpSuite(EXE)
- 零数据迁移 ，`menu.json` /`exe-tools.json` 完全不动
- 零后端改动 ，所有 Rust 代码不动
- 如果将来真的需要完全合并存储，方案 A 的 UI 层可以作为方案 C 的上层直接复用
什么时候该选方案 C？

- 当`exe-tools.json` 里的工具数量 > 20 个，且分布在多个业务分类中时
- 当你需要"在分类设置里直接管理手动录入工具"（增删改都在分类编辑弹窗里完成）时
- 当你愿意投入一周时间做全链路重构时
## 五、一句话总结
文档的方向是对的，但"为了消除 (EXE) 后缀就做全量重构"性价比不高。 当前架构在功能上已经支持混合，只是 UI 没有合并展示。如果目标仅仅是消除并列分类， 前端展示层改 3 个文件（stores/categories.ts、SideBar.vue、ToolCard.vue）即可解决 ，不需要碰 Rust 模型、存储层和数据迁移。
